Use after a v5 merge to confirm staging deployed it, or against a local `npm start`. Works on macOS, Linux and Windows.

# Verify v5

One command proves a v5 deployment. It passes only when every check below passes.

| Check | Passes when |

| sandbox reset median ≤ 1.5 s (5 resets) | **Hard FAIL on every target** (staging, production, local); no warn mode, and no flag, argument or environment variable can skip it or change the budget, sample count, timeout or idle cap (`reset-time.mjs` reads neither `process.env` nor argv; `checks.test.mjs` scans its source and runs it with override env vars and flags set). In the visitor's own sandbox, 5 resets are timed (`reset-time.mjs`). Each sample runs from the **Reset demo click** until the post-reset page is **ready**. Ready means all of these hold on the same **check**, and each check is atomic: seeded-at, `<main>`, the row count and then the URL are all read in that one check, and if any read throws, the check is discarded (nothing carries over from an earlier check) and ready is not evaluated until the next whole check: (1) the URL path is exactly `<base>/app` with query `reset=1` (a redirect elsewhere, or no redirect, never counts, even if the new page renders there); (2) the sandbox's `seeded-at` datetime in the DOM is **new**, different from the value read before the click, so the old page never counts; (3) the **main content has rendered**: the `<main>` landmark is visible and, inside it, the portfolio table shows exactly the default seed's job count of visible `job-link` rows (4; 5 rows fails like 3) (the rows **portfolio loads from Postgres** counts). Network idle is **not** part of the pass rule. Passes when **all 5 succeed** and the **median ≤ 1,500 ms** (`RESET_BUDGET_MS`, locked by `checks.test.mjs`). The 20 s timeout bounds the **whole sample**: a ready seen more than 20,000 ms after the click (even by a slow poll) is an error, never a recorded time. Any reset error or timeout fails (a page whose seeded-at never changes, or whose main content never renders, times out), as do fewer than 5 samples. The output line lists all 5 values and the median. For information only, it also lists the **idle-inclusive** time per reset and its median: ready plus no request in flight for 500 ms, the crawl's `networkidle` window, which includes Next's link prefetches. The idle watch is capped at 3,000 ms after ready (`RESET_IDLE_CAP_MS`) and shows `capped` when the network is still busy then. That number is labelled `info only, not in the pass rule` and can never change pass or fail. `reset-times.json` stores both, with the idle numbers under `infoOnlyNotInPassRule`. `reset-mustfail.test.mjs` runs the step in real Chromium against fake pages: good, chatty-network and never-quiet (idle `capped`) pages pass; slow, stale seeded-at, no `<main>`, no rows, 5 rows, late rows, no redirect, a redirect to the wrong path, and a URL that only arrives on checks whose reads throw fail. CI's `verify-v5 must-fail browser` job (`verify-v5-mustfail`) runs it, with the crawl, portfolio, and stress-seed must-fail files. The `verify-v5 skill smoke` job does not. **Fail fast with a reason** (the signoff502b incident: the reset server action was cut off, Railway logged `POST 499`, and the sample only said "not ready" 20 s later): a sample fails **at once**, not at the timeout, when the reset POST answers HTTP ≥ 400 (499, 5xx) or fails on the network with a hard disconnect (not `net::ERR_ABORTED` — Next.js soft-nav after reset redirect; that abort is remembered, and if the sample then times out the reason is `reset POST /app net::ERR_ABORTED at N ms, then not ready`, not a bare "not ready". `net::ERR_NETWORK_CHANGED` is a hard disconnect and still fails at once), or when a check sees an error screen (Next's built-in "This page couldn’t load" / "Application error" screens, or the app's PR #15 boundary by its `route-error` / `global-error` marker or its "Page load failed" / "Shell load failed" heading); an error screen is never ready. | Check | Passes when |
|---|---|
| No horizontal overflow at 320 and 390 | `max(documentElement.scrollWidth, body.scrollWidth)` ≤ the crawl viewport width (320 or 390), not `clientWidth`. A page whose layout viewport grew with the content still fails. A 422 px wide block at a 320 viewport fails `document scrollWidth 422px > viewport 320px`. The same block at 1280 does not. |
| Tap targets | At widths ≤ 480, every visible `a`, `button`, `input`, `select`, `textarea`, `summary`, `[role=button]` and `[role=link]` is at least **44×44 CSS px** (`getBoundingClientRect`, not rounded up). Hidden controls and `pointer-events: none` are skipped. |
| Text size | At widths ≤ 480, every visible text node is at least **12px** (secondary labels included). Text in `input`, `textarea` and `select` is at least **16px**, because iOS Safari zooms the page when a focused field is smaller than that. |
| One tap to the first action | On `/app` at widths ≤ 480, the first `data-testid="next-step"` or `data-testid="role-primary-action"` for that role (`data-role`) is a visible link or button, fully in the viewport, not inside a closed `<details>`, and its text starts with the role's verb: executive **Open**, PM **Approve**, superintendent **Submit**, foreman **Report**. |
| Job strip inside the viewport | At 320 and 390, no visible element inside `[data-testid="job-strip"]` has `getBoundingClientRect().right` greater than `documentElement.clientWidth`. A scrolling row of `flex-shrink: 0` pills fails `job-strip element "I-5 Culvert 24-077" right 373 > clientWidth 320`. The wrapped strip, whose pills sit inside the viewport, passes. This is 5.0.4-0 clause 2. It uses the same gate as the other rows in this table. A strip with `overflow-x: auto` can keep document `scrollWidth` inside the viewport while a pill still ends past `clientWidth`, so clause 1 does not cover it. |
| Clipping | A clip is `scrollWidth > clientWidth` on an element with `overflow-x` of `hidden` or `clip`, or `text-overflow: ellipsis` that actually truncates. The deepest such element is the one that counts, except when that element's own clipping hides protected content (money, a status pill, a table header, or an h1 / page title) whose box sticks out of it: the container is still reported, under that protected content's class, even when a child is clipped on its own. **Every** clip is counted (`clipCount`). A list shorter than `clipCount` fails, so a cap cannot hide a later one. Kind comes from what is **inside the clipped box** (the element, a descendant, or an ancestor that is that thing): a **status pill** (`data-status`), **money** (`data-cents` or a `$` amount anywhere in the clipped text, so `Budget $1,234,567` is money), a **table header** (`th` or `data-clip="header"`), then an **h1 or page title** (`h1`, `data-testid="page-title"`, `data-clip="title"`). Those four never clip, at any width, even when a title holds the full text. Sitting inside `header` does not make anything secondary. **Any** other clipped text fails at desktop widths (**≥ 768**). At **≤ 480 only**, a **secondary** label (the job strip, the company name, or `data-clip="secondary"` — the element or an ancestor that is that label) may use `text-overflow: ellipsis`, and only when its **own** `title` or `aria-label` equals the full text after trimming, or a proven expansion is open (`aria-expanded="true"` and `aria-controls` points at a different visible element whose text equals the full text). An ancestor's title, a title that merely contains the text, and a link `href` do not count. `overflow: hidden` or `clip` without `text-overflow: ellipsis` is a hard clip and fails. |

Numbers are read from the job page the user sees: each KPI tile and cost-tree row carries its exact cents in `data-cents` / `data-*-cents` next to the rendered dollars. Raw values are in `numbers.json`.

**Allowed empty states, by name only.** An empty-state message is a leaf element whose whole text starts like "No … yet / found / to show / available", "Nothing here / yet / to show", "No data" or "0 jobs" (prose that merely contains "empty" is not one). Two seeded states are legitimately empty and are allowed explicitly in `checks.mjs` `ALLOWED_EMPTY`: "No lines yet" inside the **Voided CO-001 on 24-077** and inside the **Draft CO-001 on 24-118** (matched on page path, `data-co-number` and `data-status`). The same text anywhere else, in another CO, or in a CO-001 with another status fails. Add a new allowance only by name, never by widening the pattern.

Each run signs in as a new visitor, so it gets its own sandbox and never touches anyone else's data.

## Run it

Prerequisites: Node 24 and `npm ci` in `v5/` (the script loads Playwright from `v5/node_modules`). Install the browser once with `npx playwright install chromium` from `v5/`.

```sh
git fetch origin
node .cursor/skills/verify-v5/verify.mjs                  # staging; expects last origin/main commit that touches v5/
node .cursor/skills/verify-v5/verify.mjs --wait 1800      # poll up to 30 min for the deploy to land
node .cursor/skills/verify-v5/verify.mjs --url https://demo.pcserp.app   # production: expects the newest v5 release tag
node .cursor/skills/verify-v5/verify.mjs --url http://localhost:3100 --commit "$(git rev-parse HEAD)"
node .cursor/skills/verify-v5/verify.mjs --shots /tmp/m1-screens  # also copy the screenshots somewhere handy
node .cursor/skills/verify-v5/verify.mjs --self-check     # no network/Playwright; CI unit smoke for imports + default commit
node .cursor/skills/verify-v5/verify.mjs --rc <40-char SHA>   # 5.0.4 RC handover: staging must serve this rc/5.0.4 head
node .cursor/skills/verify-v5/default-commit.test.mjs     # scripted check (includes --self-check)
node .cursor/skills/verify-v5/status-ci-gate.test.mjs     # /status ci-gate must be pass
node .cursor/skills/verify-v5/checks.test.mjs             # must-fail self-tests for every check below (no network)
node .cursor/skills/verify-v5/crawl-mustfail.test.mjs     # real crawl vs a fake localhost site: 500s (incl. a Part C plan page, a /changes page and a /schedule page), ~1.6 s pages, a /changes page with 0 items, coming soon on /schedule, a schedule missing at one width, an excluded role's schedule link, stub, short drill-down discovery, … must fail; seed child env has no VERIFY_TOKEN
node .cursor/skills/verify-v5/reset-mustfail.test.mjs     # reset timing in Chromium: stale seeded-at, no <main>, 0/5 rows, wrong/no redirect, slow must fail
node .cursor/skills/verify-v5/portfolio-mustfail.test.mjs # portfolio step: late rows pass; 0, 3, 5, hidden, 0→4→5, 0→4→0 must fail
node .cursor/skills/verify-v5/stress-seed-mustfail.test.mjs # passwords, the closed-port connection, and the stress-seed failure modes
DATABASE_URL=postgres://… node .cursor/skills/verify-v5/stress-seed.mjs --url http://localhost:3101  # against a server started with V5_SEED_STRESS=1
# DATABASE_URL may carry any password (/ ? # @ % " \): stress-seed.mjs parses it with db-url.mjs (the product's
# PR #8 approach, copied, not imported), hands postgres() only the percent-encoded form, and redacts every
# line it prints or writes (including JSON-escaped forms of secrets); an unusable URL exits 2 without echoing it.
# After npm ci + db:prepare + build + Playwright Chromium in v5/:
GIT_COMMIT_SHA="$(git rev-parse HEAD)" DATABASE_URL=postgres://… bash .cursor/skills/verify-v5/run-local-browser.sh
```

CI job `verify-v5 skill smoke` (in ci-gate) runs on changes to `v5/`, `.cursor/skills/verify-v5/`, or `ci.yml`. It runs the unit smoke, then builds v5 against Postgres and invokes `run-local-browser.sh` (full Playwright flow on `http://localhost:3100`) with a throwaway `VERIFY_TOKEN=ci-verify-v5-skill-smoke` so the stamp path is exercised. `run-local-browser.sh` first runs the **stress seed** check on a second server (`STRESS_PORT`, default `PORT+1`), then the full flow. It refuses a busy port (either one) and kills each next-server process group on exit.

**No stamp:** there is no `--no-stamp` flag; `verify.mjs` stamps only when `VERIFY_TOKEN` is set in the runner environment. To check staging without stamping, run it with `VERIFY_TOKEN` unset.

**Run conditions.** On a shared host, a staging run is the only thing using the machine's containers: nothing may create, start, or stop a container or a network while that run is in progress. A reset POST that answers HTTP 499, or that fails with `net::ERR_NETWORK_CHANGED`, is a reported FAIL. It is not a reason to start the run again quietly. The hold that keeps other work off the machine lives in the box tooling (`hold.sh`), not in this skill.

Crawled pages must not show (case-insensitive, **visible text** / `innerText` only): `coming soon`, `TODO`, `lorem`, `placeholder`, `ERP`, `not implemented`, `stub` (also `stubs`, `stubbed`), `FIXME`, `TBD`, `WIP`. The words are matched on word boundaries, so "stubborn", "Stubbs", "wipe" and "Superintendent" pass (see `checks.test.mjs`). Pitbull is construction project controls, never an ERP. Note: WIP is also a construction-accounting term (WIP schedule). It is banned today because nothing in v5 uses it; if a real WIP report ships, allow it by test id in `checks.mjs`, not by dropping the word.

**Full SHAs everywhere.** Every commit comparison uses the full 40-char SHA (`shaMatches` in `checks.mjs`). When `/health` and `/status` expose a full 40-char deploy SHA, compare exactly. A legacy 12-char prefix must still be a prefix of the expected full SHA **and** `git rev-parse --verify <prefix>^{commit}` must resolve it to exactly that commit. An unknown or ambiguous prefix fails. `git fetch origin` first. `/status` also lists applied drizzle migration tags (Verify can read staging migration state without DB access).

**Red main.** For staging/production runs (`--main-ci auto`), the skill reads the `ci-gate` check run (latest attempt) for main HEAD and for the newest `origin/main` commits that touch `v5/` (`main-ci.mjs`; `gh api` when installed, else the public GitHub API, with `GH_TOKEN`/`GITHUB_TOKEN` only if already set). Results, also in `main-ci.json`:
- **last green** = newest v5 commit whose ci-gate concluded `success`. It is the default `--commit`. FAIL when there is none.
- **staging serves the last green main commit**: FAIL unless the deployed commit (prefix resolved via git) equals last green, also when `--commit` is pinned.
- **staleness**: FAIL when the last green has been superseded by non-green v5 commits for more than `--max-green-age-hours` (default 24), measured from the commit time of the oldest v5 commit newer than last green. A quiet main (last green is the newest v5 commit) never goes stale.
- **`main HEAD red: <sha>, CI failing`** (and `newest v5 commit red: <sha>` when that differs): a **WARN**. WARNs do not change the exit code, but they are printed as `WARN …` lines, counted in the `summary:` line and the `VERIFIED … (N WARN)` line, and stored in `result.json` `warnings`. Never drop or hide them when reporting. A pending or missing ci-gate on HEAD is a `CI not green yet` WARN.

**Production.** Production runs a release tag, not main, so a production target (see `--target`) uses this rule in place of **staging serves the last green main commit**. There is no flag that skips it.
- **newest v5 release tag found**: the tags on `origin` (`git ls-remote --tags origin`, annotated tags peeled to their commit) are filtered to `v5.MINOR.PATCH` exactly (no leading zeros, no `-rc` or other suffix; `v4.*`, `v6.*` and malformed names are ignored) and ordered by **semver**, never by creation date or listing order (`v5.0.10` > `v5.0.9`, `v5.1.0` > `v5.0.2`). FAIL when there is none. It **never falls back** to last green main: with no tag the expected commit is empty and every commit check fails.
- **release tag ci-gate green**: the tag commit's `ci-gate` check run (latest attempt) concluded `success`. Failure, pending or missing is FAIL.
- **release tag commit is on main**: GitHub `compare/<tag commit>...main` is `ahead` or `identical`. Not an ancestor, or unknown, is FAIL.
- **production serves the newest v5 release tag**: the deployed full SHA equals the tag commit exactly. An older tag, main HEAD, last green main or an untagged commit all fail.
- The expected commit for `/health` and `/status` is the tag commit (unless `--commit` pins one; the rule above still applies). The main-health results (**last green main commit found**, staleness, red HEAD WARN) still run; only the staging comparison is replaced.
- Logic: `resolveTarget`, `newestV5Tag`, `evaluateRelease`, `expectedCommitFor`, `commitResults` in `checks.mjs`; reads in `readRelease` (`main-ci.mjs`). `checks.test.mjs` holds the must-fail cases.

## RC flow

Two ways a version is verified. The checks themselves do not get looser in either one.

**Per PR (5.0.2 and 5.0.3).** Each green PR is verified on its own after it merges to `main`. Staging is expected to serve the last green main commit. `--rc-version 5.0.2` or `5.0.3` is refused even when `--rc` is omitted (`5.0.2 stays on the per-PR flow; RC handover starts at 5.0.4`). Those runs do not execute the phone layout checks.

**Per RC (from 5.0.4).** Each green 5.0.4 PR merges into branch `rc/5.0.4`, cut from `main`. The lead deploys that branch's head to staging and hands it over once. verify-v5 then runs against that exact SHA:

```sh
git fetch origin
node .cursor/skills/verify-v5/verify.mjs --rc <40-char SHA>
node .cursor/skills/verify-v5/verify.mjs --rc <40-char SHA> --rc-version 5.0.4
```

The verdict is for that SHA. The run still does the trust bar: every check in the table above (banned words, the nav crawl and its 1.5 s budget, reset median ≤ 1.5 s, `/status`, M2/M4/M5). It also runs the phone layout checks, including the clipping rule, which a per-PR verify does not. This mode does not skip or relax any trust-bar check. The one comparison it does not apply is **staging serves the last green main commit**, because the deploy is the rc head, not main. Production is refused (`RC handover is staging; production keeps the release-tag rule`). A `--commit` that disagrees with `--rc`, or a SHA that is not 40 hex characters, exits 1 before the browser starts. If the browser cannot reach `/status`, the run writes `rc.json` and prints `FAIL /status unreachable` instead of only `verify-v5 crashed`.

On top of the trust bar, an RC run checks:

| Check | Passes when |
|---|---|
| staging `/status` serves the rc head | The commit on `/status` is exactly the `--rc` SHA. A full SHA that differs fails `staging serves <got>, rc head is <sha>`. A shorter prefix passes only when git resolves it to that same SHA (the same rule as `shaMatches`). `/health` still has to match the same expected SHA. |
| rc history | `git log --first-parent origin/main..<sha>` lists what landed on the rc. A commit is a merged PR when its subject is `Merge pull request #N` or ends with `(#N)`. Other commits are skipped. The files for each PR are `git diff --name-only <sha>^1 <sha>`. The check names the PR numbers and how many drizzle tags the rc journal adds over main. `rc.json` stores the full list. If the SHA is not local, the run fetches `origin rc/5.0.4`. A fetch or git failure is a failing `rc history` check. It does not skip the browser run. |
| rc migrations apply and the app is healthy | Every journal tag present on the rc and absent on main must appear in `/status` `status-migrations`, the rc journal's `when` values must strictly increase (drizzle skips a migration whose `when` does not), and `/health` must be 200 with status `ok` and db `ok`. No added migration does not add a second health failure; `/health` is already its own check. |
| acceptance items for 5.0.4 | Every item in `docs/v5/specs/5.0.4-*.md` **at that SHA** (`git ls-tree -r --name-only <sha> docs/v5/specs/`, then `git show <sha>:<path>`, not the working tree). Listing `docs/v5/specs` without `-r` and a trailing slash returns only the directory, which is not a spec. The heading `### Acceptance check for 5.0.4-0` is one item. Each numbered `**Title**` under `### Checks for 5.0.4-a` through `5.0.4-g` is one item. A Checks section with no numbered titles (5.0.4-f) is still one item. Today the run executes **5.0.4-0** only, both clauses of that acceptance sentence: the nav crawl's document `scrollWidth` ≤ the 320 and 390 viewport, and no visible element inside `[data-testid="job-strip"]` has `getBoundingClientRect().right` greater than `documentElement.clientWidth` at those widths. That item fails when any crawl row reports `document scrollWidth` or `job-strip element`, and it fails `not executed` when the nav crawl did not run. The job-strip clause is recorded only when phone checks are on (`--rc` at 5.0.4 or later, or `--phone-checks`), the same gate as clause 1 and the other phone layout checks. A per-PR crawl does not record it. Clause 2 is gated that way because it is the second half of the same 5.0.4-0 sentence clause 1 already runs under, and the acceptance item is an RC handover check. Sections **5.0.4-a through 5.0.4-g** fail closed as `not executed` until a later run performs them. They are not marked pass. |
| ellipsis/clipping at ≤ 480 | Any nav-crawl failure whose text contains `clipped ` at 320, 375, or 390. This is the clipping rule above, called out for the handover. A clip at ≥ 768 still fails the nav crawl. It is not dropped. |

A FAIL names the PR it traces to. `attributeChecks` in `rc.mjs` attributes **each failure line on its own** against `CHECK_PATHS` (first rule wins on that line) and keeps the merged PRs, newest first, whose diff touches those paths. A crawl detail shaped `summary — failure; failure` keeps that summary on each attributed line (`summary — failure — PR #N`), so an overflow line and a clipping line can name two different PRs. One failure line still reads `detail — PR #24`. A check with no path rule says `no file map for this check`. A rule whose paths no merged PR changed says `no merged PR on the rc changes <paths>`. Passing checks are not rewritten. The printed `FAIL` line and `rc.json` `attributions` both carry the PR numbers. The trace uses only the rc's merge history and the files those merges changed. It does not guess from a PR that did not touch the mapped paths.

`--self-check --rc <sha>` prints `self-check ok expected=<sha> rc=5.0.4 branch=rc/5.0.4` and exits before Playwright. `checks.test.mjs` must-fails a `/status` commit that is a different SHA than the rc head, and must-fails an attribution that names a PR whose files are unrelated to the failing check.

**Default commit (no network):** for `--self-check` and local runs, `resolveDefaultCommit` runs `git log -1 --format=%H origin/main -- v5/` (see `default-commit.mjs`). If that history is empty it falls back to `git rev-parse origin/main`. Pass `--commit` to pin a SHA (local `npm start`, a lagging deploy, or a deliberate mismatch). On an RC run the expected commit is the `--rc` SHA, not this default.

**Last-verify stamp:** on a passing run, the script `POST`s `/api/verify/stamp` when `VERIFY_TOKEN` is set in the runner environment. The same value must be configured on the Railway staging service (`VERIFY_TOKEN`). The stamp must match the deployed commit and must not use a future timestamp. Without the token, `/status` keeps showing `not recorded`. If `VERIFY_TOKEN` is set and the stamp fails (including HTTP 401), verify-v5 exits **non-zero**. The token is used only for that request: seed subprocesses (`tsx`) get an allowlisted env only (`SEED_CHILD_ENV_ALLOW` in `drill.mjs`: PATH, HOME, temp dirs, locale, TZ), and the seed loader fails if its child reports any other parent variable (`VERIFY_TOKEN`, `DATABASE_URL`, …).

To see it fail on purpose, pass a commit staging doesn't serve, such as `--commit 000000000000`. The commit checks print `FAIL` and the run exits 1.

Exit code 0 means every check passed (and stamp succeeded when `VERIFY_TOKEN` was set); `WARN` lines may still be present and must be reported. Exit code 1 means at least one failed; the printed `FAIL` lines say which.

## Evidence

Each run writes `.cursor/skills/verify-v5/evidence/<UTC timestamp>/` (git-ignored):

- `result.json` lists every check, pass or fail, with the observed value. On an RC run a failing check's detail ends with the PR it traces to.
- `rc.json` (only when `--rc` is set) holds the rc version, the exact SHA, the branch, the `/status` commit, the migrations label, every merged PR with its files, the migration tags added over main, whether the journal `when` values increase, the spec path, and `attributions` for every failing check (`name`, `prs`, `detail`).
- `health.json` holds the raw `/health` status code and body.
- `status.json` holds the values read from the `/status` page by test id.
- `status.png` is a full-page screenshot of `/status`.
- `main-ci.json` holds main HEAD, the v5 commits read, their ci-gate, the deployed full SHA and the red-main results.
- `crawl.json` has the crawl `plan` and every crawl load (status, timings, overflow, empty hits, errors; drill-down loads carry `drill: true`) plus `slowest`, `slowestDrill` and `failures`, and `drill` with the derived `seedItems`, `itemCount`, `access`, the per role×width load `plan`, every job-page `discovery`, `discoveryFailures` and `coverageFailures`, and `partC` (`Part C crawl check 4`: seed `active` jobs, `planLinked` items, one record per role × width × active job with the cost item and plan paths and the plan link's source, `failures`, `slowest`; those rows carry `partC: "cost-item" | "plan"`); screenshots in `<shots>/crawl/`.
- `failures/` (only when something failed): one capture per failed reset sample, failing crawl / drill-down / Part C load, and short drill-down discovery, written while the page still shows it: `NNN-<kind>-<role>-w<width>-<path>.png` (full page), `.html` (page HTML) and `.json` (`reason`, `url` with its query, `consoleErrors`, `pageErrors`, `failedRequests` with method, URL and status). Reset samples and crawl rows name their file under `evidence`. Nothing secret is written: VERIFY_TOKEN, GH/GitHub tokens, the DATABASE_URL and its password and the page's cookie values are replaced with `[redacted]`, as are Authorization / Cookie / token headers and secret-named or token-looking query values; cookies themselves are never saved. At most 60 captures per run. Every evidence JSON (`failures/*.json` including its `extra`, `health`, `main-ci`, `status`, `crawl`, `numbers`, `reset-times`, `result`, the stress-seed `--out`) is written with `safeJson`: strings are redacted while still raw, then the JSON text is scanned again, so a `"` or `\` in a secret can't slip through as `\"` or `\\`. All secret matching goes through ONE function, `scrubSecrets` (`evidence.mjs`): rather than listing spellings, it decodes the text (HTML character references named, decimal and hex; JS/JSON escapes including `\uXXXX`, `\u{...}` and `\xHH`; percent-encoding as UTF-8, which covers the URL path, query, `encodeURIComponent` and URLSearchParams forms; `+` as a space, also tried with `+` kept), in any mix and any hex case, up to 4 levels deep (so JSON twice, HTML twice or three times, `\u` inside JSON as in a Next.js flight script, `%25` double-encoding), looks for the secret in every decoded view and replaces the original characters it came from. The `.html` is redacted at the DOM level first (`redactedDocumentHtml`: `scrubSecrets`, its source sent into a CDP isolated world the page's scripts can't see, runs over every text node including script text, comment and attribute value of a detached copy of the document, so the live page is untouched), then by `redactText` over the serialized text, which also covers the serializer's partial escaping (text nodes: `& nbsp < >`, quotes raw; attribute values: `& nbsp "`, plus `< >` in newer Chromium). Console and page-error text is cut to 2000 chars only after redaction, so a cut can't keep a secret's prefix. Every printed line (including crash output) goes through `redactText`. Named HTML character references are matched with or without a trailing `;` (`&quot` and `&quot;` both decode), by the longest name `scrubSecrets` knows, so a secret written that way is still replaced in its decoded form. `safeJson` then scrubs secrets only inside JSON string literals and `JSON.parse`s the result before writing: a secret that looks like JSON punctuation cannot eat the structure, and a broken scrub throws instead of being saved. Console and page-error text is capped at 100,000 characters while still raw; a secret that straddles that cut is replaced in the kept head (the scan looks past the cut far enough to see an encoded form such as `&amp;`), so the file does not keep a prefix of it. A value that appears both under `slowest` and under `rows` is written out in both places. `[circular]` is only for a real cycle. Not covered: base64 and other non-escape encodings. A secret only in a live `value`, a shadow root or a child frame's own document is not in the saved `.html` at all, but the screenshot can still show it.
- `numbers.json` has the raw M2 / M4 / M5 values and the evaluation; `m2-after-approve.png`, `m4m5-before.png`, `m4m5-after-approve.png`.
- `login-desktop.png`, `portfolio-desktop.png`, `assistant-rail-desktop.png`, `job-desktop.png`, `foreman-chat-mobile.png`, `portfolio-mobile.png` and `job-mobile.png` show each flow (in `--shots` when given).

## Why a deploy may lag

Staging `pitbull-web` deploys `main` from `/v5` with Railway's wait-for-CI on. A deploy sits in `WAITING` until every GitHub Actions run on the commit finishes, including CodeQL. Railway skips the deploy if any run fails, including a Dependabot security-update run, and skips commits that touch nothing under `/v5`. Use `--wait` after a merge, then check the Railway deployment list when the commit never arrives.

The pre-deploy step `npm run db:ensure` creates the `DATABASE_URL` database when it is missing. It never drops or alters anything.
