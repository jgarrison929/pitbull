## Problem

On `main`, each cost item has a required `planned_start_on` and `planned_finish_on`, and planned value spreads Current Budget linearly between those dates (`plannedValueCents` in `v5/src/lib/ev.ts`). There is no activity, relationship, calendar, or baseline table. A prospect who asks to see the schedule sees nothing. Daily plan lines carry a free-text `activity` field that links to nothing.

InEight Schedule is a CPM planning and risk tool (C1). Control gets schedule dates by manual entry, a cost item import, or an XER import, and each cost item's Schedule ID must equal the activity ID (C34). When activities are finer than cost items, the documented workaround is summary activities, an Excel export, and a hand join to a Control import template (C35). Schedule's only native product link is Estimate (C32). That file hand-off is the weakness Pitbull can beat (I1).

## Users and roles

Pitbull 5.0 has four demo roles. 5.1 does not add a scheduler role. The PM owns the schedule, the way the Estimator was folded into the PM for 5.0.0.

| Role | Owns in 5.1 | Reads |
|---|---|---|
| Project Manager | Create and edit activities, links, and the calendar. Set and re-baseline. Import a schedule file (5.1.3) | Job Gantt, float, SPI |
| Superintendent | Link a daily plan line to an activity when planning the day | Gantt and today's activities |
| Foreman | Nothing new | The activity name on today's plan line |
| Executive | Nothing new | Portfolio finish dates and SPI |

InEight splits organization roles (Schedule creator, Project member, Administrator) from per-schedule contributor roles (Scheduler, Short Interval Planner, Markup, View Only) (C4, C5). Mid-size heavy-civil contractors rarely staff a full-time scheduler on every job. Folding schedule edits into the PM keeps the role surface small and matches the demo.

## InEight comparison

What we copy, with claim IDs:

- Activities with durations, calendars, and working days (C8, C10).
- Finish-to-start and start-to-start logic with lag (C9). CPM-lite leaves out finish-to-finish and start-to-finish (recommendation 4).
- A locked baseline that cannot be edited (C6, C7). Snapshots in InEight are a separate, two-slot feature (C14). Pitbull keeps one current schedule and a list of immutable baselines.
- SPI from a time-phased budget whose dates come from the schedule (M5, and C8/C9 in the cost and earned value intel). The default spread stays linear (I3).

What we refuse to copy:

- Schedule ID typing and XER round-trips into Control (C34 to C37). Activities link to cost items by key in one database (I1, recommendation 1).
- Percent complete typed on the Gantt chart (C19, C20). Approved daily reports drive EV. The schedule only reads percent complete (I5, recommendation 5).
- Monte Carlo, risk registers, markup cycles, AI schedule generation, and the Knowledge Library (C25 to C31, I7, recommendation 9).
- Binary Microsoft Project `.MPP` import. XER and Microsoft Project XML cover both tools without a binary parser (I6).

## Scope

### In scope for 5.1

1. Activities on a job, with a code, a name, a duration in whole working days, and early and late dates.
2. One working calendar per job (Monday to Friday by default, plus holiday dates).
3. Many-to-many links between activities and leaf cost items. A cost item's current dates are the earliest start and latest finish of its linked activities (I2, recommendation 1).
4. A Gantt view per job, with bars for current dates and, after 5.1.2, a baseline bar.
5. Finish-to-start and start-to-start dependencies with whole-day lag, forward and backward pass, total float, and the critical path (recommendation 4).
6. A baseline that cannot be edited. Planned value reads baseline dates, never current dates (I4). The spread stays linear. A CPM finish date is a full working day, so the mapping passes finish + 1 day into `plannedValueCents` (acceptance check 7 in the schedule intel).
7. Daily plan lines link to an activity. The free-text `activity` column becomes the activity's name when linked (recommendation 6).
8. XER import, then Microsoft Project XML import, all-or-nothing with row errors (recommendation 7, I6). Final 5.1 increment.

### Out of scope for 5.1

- Finish-to-finish and start-to-finish links, negative lag, multiple calendars per job, constraints other than "start no earlier than", resource leveling, and resource histograms (recommendation 4).
- Monte Carlo, risk registers, markup, AI schedule generation, and program-level schedules (recommendation 9).
- Binary `.MPP` import (I6).
- Typing percent complete on the Gantt chart (I5).
- Time-phased forecasting and non-linear cost curves (cost and earned value intel, "Leave out for 5.0.0").

## Planned value rules (locked)

These rules are not open questions. Every 5.1 increment obeys them.

1. **Wording.** Planned value is "PV dates from the baseline schedule, linear spread". The plan section 9 phrase "PV from schedule instead of linear" is replaced by that wording (I3, recommendation 2).
2. **Baseline dates only.** After the first baseline exists, `plannedValueCents` and `plannedAsOfSql` read baseline start and finish for each cost item. Current activity dates drive the Gantt chart and the forecast finish. They never enter PV (I4). Before the first baseline, PV keeps reading `cost_items.planned_start_on` and `planned_finish_on`, which 5.1.0 keeps in sync with current activity dates so the S-curve does not go blank.
3. **Finish + 1 day.** A CPM finish date is inclusive. The call into `plannedValueCents(budget, start, finishExclusive, asOf)` passes the day after the CPM finish. Passing the finish date unchanged reaches the full budget one day early (schedule intel, acceptance check 7).
4. **Pacific dates.** The as-of date is America/Los_Angeles, the same fix as finding D7 in the cost and earned value intel.

## Data model sketch

Builds on `cost_items.planned_start_on`, `planned_finish_on`, and `plannedValueCents` / `plannedAsOfSql`. One module owns schedule writes so the seed, the screen, and the assistant cannot diverge (no split ownership).

```ts
// v5/src/db/schema.ts (sketch)

export const linkTypeEnum = pgEnum("schedule_link_type", [
	"finish_to_start",
	"start_to_start",
]);

/** One working calendar per job. Holidays are dates with no work. */
export const jobCalendars = pgTable(
	"job_calendars",
	{
		id: uuid("id").primaryKey(),
		companyId: companyRef(),
		jobId: uuid("job_id")
			.notNull()
			.references(() => jobs.id, { onDelete: "cascade" }),
		name: text("name").notNull(),
		/** Bitmask: bit 0 = Monday ... bit 6 = Sunday. Default Mon-Fri = 31. */
		workdaysMask: integer("workdays_mask").notNull().default(31),
	},
	(t) => [uniqueIndex("job_calendars_job_uidx").on(t.jobId)],
);

export const calendarHolidays = pgTable(
	"calendar_holidays",
	{
		id: uuid("id").primaryKey(),
		companyId: companyRef(),
		calendarId: uuid("calendar_id")
			.notNull()
			.references(() => jobCalendars.id, { onDelete: "cascade" }),
		on: date("on").notNull(),
		name: text("name").notNull().default(""),
	},
	(t) => [uniqueIndex("calendar_holidays_day_uidx").on(t.calendarId, t.on)],
);

export const activities = pgTable(
	"activities",
	{
		id: uuid("id").primaryKey(),
		companyId: companyRef(),
		jobId: uuid("job_id")
			.notNull()
			.references(() => jobs.id, { onDelete: "cascade" }),
		code: text("code").notNull(),
		name: text("name").notNull(),
		/** Whole working days. */
		durationDays: integer("duration_days").notNull(),
		/** Optional "start no earlier than" constraint. */
		startNoEarlierOn: date("start_no_earlier_on"),
		earlyStartOn: date("early_start_on").notNull(),
		earlyFinishOn: date("early_finish_on").notNull(),
		lateStartOn: date("late_start_on").notNull(),
		lateFinishOn: date("late_finish_on").notNull(),
		totalFloatDays: integer("total_float_days").notNull().default(0),
		isCritical: boolean("is_critical").notNull().default(false),
		/** Bumped on every write. A save with a stale version is refused (I8). */
		version: integer("version").notNull().default(1),
	},
	(t) => [
		uniqueIndex("activities_job_code_uidx").on(t.jobId, t.code),
		index("activities_job_idx").on(t.jobId),
	],
);

export const activityLinks = pgTable(
	"activity_links",
	{
		id: uuid("id").primaryKey(),
		companyId: companyRef(),
		jobId: uuid("job_id")
			.notNull()
			.references(() => jobs.id, { onDelete: "cascade" }),
		predecessorId: uuid("predecessor_id")
			.notNull()
			.references(() => activities.id, { onDelete: "cascade" }),
		successorId: uuid("successor_id")
			.notNull()
			.references(() => activities.id, { onDelete: "cascade" }),
		type: linkTypeEnum("type").notNull().default("finish_to_start"),
		lagDays: integer("lag_days").notNull().default(0),
	},
	(t) => [
		uniqueIndex("activity_links_pair_uidx").on(
			t.predecessorId,
			t.successorId,
			t.type,
		),
	],
);

/** Many activities ↔ many leaf cost items. */
export const activityCostItems = pgTable(
	"activity_cost_items",
	{
		activityId: uuid("activity_id")
			.notNull()
			.references(() => activities.id, { onDelete: "cascade" }),
		costItemId: uuid("cost_item_id")
			.notNull()
			.references(() => costItems.id, { onDelete: "cascade" }),
		companyId: companyRef(),
	},
	(t) => [
		primaryKey({ columns: [t.activityId, t.costItemId] }),
		index("activity_cost_items_item_idx").on(t.costItemId),
	],
);

export const scheduleBaselines = pgTable(
	"schedule_baselines",
	{
		id: uuid("id").primaryKey(),
		companyId: companyRef(),
		jobId: uuid("job_id")
			.notNull()
			.references(() => jobs.id, { onDelete: "cascade" }),
		name: text("name").notNull(),
		reason: text("reason").notNull(),
		setAt: timestamp("set_at", { withTimezone: true }).notNull().defaultNow(),
		setById: uuid("set_by_id").references(() => users.id, {
			onDelete: "set null",
		}),
	},
	(t) => [index("schedule_baselines_job_idx").on(t.jobId, t.setAt)],
);

/** Immutable copy of activity dates at baseline time. */
export const baselineActivities = pgTable(
	"baseline_activities",
	{
		id: uuid("id").primaryKey(),
		companyId: companyRef(),
		baselineId: uuid("baseline_id")
			.notNull()
			.references(() => scheduleBaselines.id, { onDelete: "cascade" }),
		activityId: uuid("activity_id")
			.notNull()
			.references(() => activities.id, { onDelete: "restrict" }),
		startOn: date("start_on").notNull(),
		finishOn: date("finish_on").notNull(),
		durationDays: integer("duration_days").notNull(),
	},
	(t) => [
		uniqueIndex("baseline_activities_pair_uidx").on(t.baselineId, t.activityId),
	],
);

// daily_plan_lines gains:
activityId: uuid("activity_id").references(() => activities.id, {
	onDelete: "set null",
}),
// `activity` text stays as the display name. When activityId is set, writes copy the activity name into it.
```

Two shapes were considered for the baseline:

1. Copy dates onto `cost_items` as `baseline_start_on` / `baseline_finish_on`. Fast to read. A re-baseline overwrites history.
2. A `schedule_baselines` row plus `baseline_activities`. History stays. PV joins through the latest baseline.

Shape 2 is the one to build. SPI honesty needs the old baseline after a re-baseline (I4, acceptance check 9). The join is per leaf cost item at read time, the same place `plannedAsOfSql` already runs.

### Call on import and plan-line links

**Daily plan lines link to activities in 5.1.0.** Recommendation 6 is Short Interval Planning without a second tool. The link needs the `activities` table from the same increment, adds no module, and makes the superintendent's plan show work against CPM dates. Leaving it for later would leave the free-text `activity` column as a second name for the same work.

**XER and Microsoft Project XML import land as 5.1.3.** Native linking is the product edge (I1). Import is how a contractor who already lives in P6 or Microsoft Project gets in, and the intel puts it after the native model (recommendation 7). With the velocity forecast, core 5.1 (5.1.0 to 5.1.2) ends on 2026-12-15. Adding 5.1.3 on 2027-01-05 (after the Dec 24 through Jan 1 skip) moves 5.2.0 to 2027-01-15. Binary `.MPP` stays out (I6). If 5.1.3 slips, import moves to the horizon rather than delaying 5.2 further.

## Trust-bar risks

- **Empty states (item 1).** A job with no activities must not show an empty Gantt shell. Harbor (draft estimate) has no Schedule nav entry until its estimate is approved. An approved job with no activities yet shows written guidance ("Add an activity to build the schedule"), not "No activities yet".
- **Banned strings (item 1).** The Gantt page names no future release. Words such as "coming soon" fail the crawl.
- **Visible proof (item 3).** SPI changes when PV moves onto the baseline. The 5.1.2 release notes and verify evidence list before and after SPI for each active job.
- **One write path (item 6).** Schedule writes go through one server module and `run()`. The seed builds rows for speed, and a replay test (same pattern as 5.0.2 field history) keeps seeded and live graphs equal on the Cedar fixture.
- **Stale saves (item 6).** Plan view in InEight does not lock concurrent edits (C24). Each activity carries a version. A save against an old version is refused with the other editor's name (I8).
- **Page speed (item 1).** The Gantt page stays under 1.5 s on staging with the seeded graphs (under 100 activities per job in 5.1).
- **Finish + 1 day (item 3).** A wrong mapping makes PV hit the full budget one day early and breaks every SPI check. The unit tests in 5.1.2 pin the intel's $217,000 / $434,000 / $651,000 / $868,000 ladder for 04-210.
