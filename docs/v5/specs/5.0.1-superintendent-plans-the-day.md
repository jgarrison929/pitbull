# 5.0.1: the superintendent plans the day

Status: **shipped** 2026-10-25 at 5:50 AM PT (tag `v5.0.1` at `05246e2e`). Spec revised 2026-10-25 at 10:57 AM (PT). Evidence: production verify 37/37 on #701. See the [roadmap](../../roadmap.md).

5.0.1 has two parts that can ship as parallel PRs:

- **Part A.** The superintendent creates a daily plan, picks the crew, and adds and removes cost-item lines. Today, plans and lines come only from the seed.
- **Part B.** A public `/roadmap` page shows what shipped and what comes next, in order.

## Why this is first

The five-minute demo in [fresh-start plan section 4](../fresh-start-plan.md#4-500-core-the-smallest-credible-ineight-style-story) has this as step 4: "the superintendent picks today's cost items and crew." On `main`, the superintendent can edit seeded lines and issue a seeded plan, but cannot start one. A prospect who asks "show me how tomorrow gets planned" sees the gap at once.

InEight's daily planning starts with a planner, "typically a superintendent, field engineer or indirect supervisor", who builds the plan and submits it to execution (claim C1 in [field plan and progress intel](../intel/field-plan-and-progress.md)). A plan can be created from scratch or from a copy (C2). 5.0.1 covers creating a plan from scratch.

Part B closes trust bar item 6: "a public roadmap (section 9) that names what comes next and in what order."

## User stories

1. As the superintendent, I create today's plan for a crew on a job, so the foreman has work to report against.
2. As the superintendent, I add a line for a cost item with activity, location, quantity, workers, and hours, and I see at once whether the planned rate is within budget.
3. As the superintendent, I remove a line I added by mistake before I issue the plan.
4. As the superintendent on a phone, I do stories 1 to 3 in the assistant: "Plan today on 25-031 for Bridge Crew 2."
5. As the foreman, I see the issued plan on my phone and report against it, using the M3 flow that already exists.
6. As a prospect who is not signed in, I open `/roadmap` and see which versions shipped and which modules come next, in order.

## Part A: plan building

### Rules

- Only the superintendent can create a plan or add and remove lines. The foreman and the PM get a refusal ("Couldn't create plan on 25-031"), and the rail shows it with refusal wording.
- A plan belongs to one job, one crew, and one date. A second plan for the same job, crew, and date is refused, and the refusal names the existing plan.
- The plan date must fall from 14 days before to 14 days after today, in America/Los_Angeles.
- A job whose estimate is still a draft can't take a plan, the same rule change orders follow. 26-010 refuses with "Approve the estimate before planning field work."
- Lines can be added or removed only while the plan is `draft`. After **Submit plan** (state `issued`), add and remove are refused. The existing `dailyPlan.updateLine` rules don't change.
- A line's cost item must be a leaf cost item on the same job. A summary WBS code, or a code from another job, is refused.
- Line values use the limits in `v5/src/lib/plan-line.ts`. Quantity, workers, and hours per worker are the fields the seeded lines already have.
- **Submit plan** refuses a plan with no lines.
- The new plan's foreman is the crew's foreman at create time. The plan keeps that name if the crew's foreman changes later.

### Typed actions

All three actions go through `run()` in `v5/src/server/assistant/actions.ts`, with `writes: true`. The job's **Changes on this job** list derives from `writes`, so the new actions appear there with no extra list to edit.

| Action | Arguments | Role |
|---|---|---|
| `dailyPlan.create` | `job`, `date`, `crew` | superintendent |
| `dailyPlan.addLine` | `job`, plan (by date and crew, or by id from the screen), `costCode`, `activity`, `location`, `qty`, `workers`, `hours` | superintendent |
| `dailyPlan.removeLine` | `job`, plan, line (by id from the screen, or by cost code in the assistant) | superintendent |

The assistant router (`v5/src/lib/assistant/route.ts`) is deterministic. It maps these two prompts:

- "Plan today on 25-031 for Bridge Crew 2" maps to `dailyPlan.create`.
- "Add 04-210 to today's plan on 25-031: 12 CY, 3 workers, 8 hours" maps to `dailyPlan.addLine`.

### Data model sketch

Two shapes were considered for the crew:

1. Keep `daily_plans.crew` as free text and offer the distinct seeded names in a picker. That puts the crew list in two places (the seed and every plan row), and leaves nowhere for the 5.0.2 labor rate to live.
2. Add a `crews` table and point each plan at it. One table owns the crew list, and 5.0.2 adds the rate as a column.

Shape 2 is the one to build. The migration moves every caller to `crew_id` and drops the text column in the same PR, so there is one way to name a crew.

```ts
// v5/src/db/schema.ts (sketch)
export const crews = pgTable(
	"crews",
	{
		id: uuid("id").primaryKey(),
		companyId: companyRef(),
		name: text("name").notNull(),
		foremanId: uuid("foreman_id")
			.notNull()
			.references(() => users.id, { onDelete: "cascade" }),
	},
	(t) => [uniqueIndex("crews_company_name_uidx").on(t.companyId, t.name)],
);

// daily_plans: replace `crew: text` with
crewId: uuid("crew_id")
	.notNull()
	.references(() => crews.id, { onDelete: "restrict" }),
// and add
uniqueIndex("daily_plans_job_crew_date_uidx").on(t.jobId, t.crewId, t.planDate),
// weather becomes optional on create (default ""), and the plan card hides an empty weather row.
```

The migration does the following:

1. It inserts one `crews` row per distinct `(company_id, crew, foreman_id)` in `daily_plans`.
2. It sets `crew_id` on every plan.
3. It drops `daily_plans.crew`.

## Part B: the public roadmap page

- `/roadmap` is public, the same as `/status` and `/changelog`. It is linked from both of those pages.
- The page lists the shipped versions, newest first. Each shipped version links to its `/changelog` entry.
- After the shipped versions, the page lists what comes next, in order: the remaining 5.0.x increments by name, then 5.1 Schedule, 5.2 Contracts and subs, 5.3 Document control, 5.4 Compliance, and 5.5 Owner billing and portfolio reporting.
- The page shows the order and no dates. Trust bar item 4 says "Nothing is announced before it passes the gate", so a date belongs on a release once it ships.
- The content lives in `v5/src/content/roadmap.ts`, next to `changelog.ts`. Railway builds from `/v5`, so the page can't read `docs/roadmap.md` at run time.
- A vitest test stops the two lists from drifting. It fails when any of these is true:
  - A version or module name in `roadmap.ts` is missing from `docs/roadmap.md`.
  - A shipped version in `roadmap.ts` has no entry in `changelog.ts`.
  - The page text contains a banned string.
- Release names on the page say "accounting and payroll export" for the 5.6+ item. The nav crawl bans the word for the other kind of business system in visible text.

## Out of scope

- Creating a plan from a copy of another plan, and creating a plan from a work package. Work packaging is a 5.6+ item.
- Crew labor rates and the crew roster. 5.0.2 adds crew rates.
- Linking a line to a schedule activity. The line's `activity` stays free text. The schedule intel recommends a link in 5.1 (recommendation 6 in [schedule intel](../intel/schedule.md)).
- Editing planned equipment on a new plan. A new plan has no equipment rows, and the plan card hides the equipment row when it is empty.
- Plans across more than one crew, and moving a line between plans.
- Any change to the foreman report, approve, and return flow from M3.

## Trust-bar risks

- **Empty states (item 1).** A new plan has no lines until the superintendent adds one. Its card needs written guidance ("Add a cost item to plan the day"), not "No lines yet". The crawl's empty-state scan allows "No lines yet" only on draft and voided change orders.
- **Banned strings (item 1).** The roadmap page names future releases. Words such as "coming soon", "TBD", "WIP", and "placeholder" fail the crawl. Use "Next" and the release order.
- **Visual baselines (item 5).** The PM job-page baseline doesn't change. The superintendent's job page gains **New plan**. Add a baseline for it at 0-pixel tolerance, the same as the others in `visual.spec.ts`.
- **Seed story (item 2).** The seed invariant test must still pass: each project has non-empty EV, at least one pending CO, and a plan for the superintendent.
- **Two crew names (item 6).** Dropping `daily_plans.crew` in the same migration keeps one name per crew.
