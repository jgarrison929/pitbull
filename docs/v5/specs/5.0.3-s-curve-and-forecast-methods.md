## Why this is third, and before or with early 5.1

[Fresh-start plan section 4](../fresh-start-plan.md#4-500-core-the-smallest-credible-ineight-style-story), step 5, asks for "an S-curve chart" and "EAC/ETC with a per-item forecast method (current budget or average performance)". Trust bar item 5 asks for "light and dark themes". None of them is on `main` yet as a shipped 5.0.3.

- No chart library is in `v5/package.json`, and no chart component is in `v5/src`.
- The `forecast_method` enum has one value, `current_budget`. Migration `0012_drop_average_performance.sql` (#675) removed Average Performance because no screen could select it.
- `globals.css` defines a `.dark` variant, but nothing in `v5/src` turns it on.
- Plan history is reconstructed from plan columns plus `action_runs`. A return then approve leaves only the last column stamps, and the UI shows actor **names** today (`buildPlanHistory` in `v5/src/server/plan-page.ts`).
- `unknownJob()` lists every job number in the sandbox, including draft Harbor (26-010).

5.1 Schedule moves planned value from each cost item's own dates onto the schedule (plan section 9). The S-curve is where that move shows, so Part A ships in 5.0.3.

InEight's time-phased budget spreads each cost item's current budget between its start and finish dates, and SPI needs that spread (claims C8 and C9 in [cost and earned value intel](../intel/cost-and-earned-value.md)). The intel concludes that daily linear planned value "is enough for the S-curve the plan asks for" (I4).

## User stories

1. As the executive on the portfolio, I see one curve of planned, earned, and actual cost across the active jobs, and I can tell at a glance whether the company is ahead or behind.
2. As the PM on a job, I see the same curve for that job. Its values at the cutoff match the KPI tiles to the cent.
3. As the PM, I set a cost item's forecast method to Average Performance. I see the item's new EAC, with the arithmetic, and the job EAC moves by exactly the change.
4. As anyone, I switch to the dark theme, and every page stays readable.
5. As the PM, I open a returned-then-approved plan and see each submit, return, and approve with the actor's **role** and the time in the company zone.
6. As the superintendent in the rail, when I name a job that does not exist, I see that number called out and up to three of my real jobs as choices.

## Part A: the S-curve

**Files and areas.** New `v5/src/server/curve.ts` with `jobCurve` and `portfolioCurve`. Job page and portfolio page chart sections. Recharts through shadcn charts (plan section 6). Reuse planned, earned, and actual expressions from `v5/src/server/cost-rollups.ts`. No schema change.

### Rules

- One point per calendar day in America/Los_Angeles, from the job's earliest cost-item planned start to its latest planned finish. The cost and earned value intel logs the UTC date problem as finding D7.
- Planned value is cumulative and linear between each leaf cost item's planned start and finish, on Current Budget. It is the same function the PV tile uses. The last planned-value point equals the job's Current Budget total.
- Earned value and actual cost follow the one-cutoff rule from #666. Both lines stop at the cutoff, which is the date of the last locked claim.
  - Earned value changes only on lock dates.
  - Actual cost is cumulative by cost-entry date. From 5.0.2 on, field labor is dated with the plan date.
  - Cost posted after the cutoff shows in the "since lock" tile, as it does today, and not on the curve.
- The curve has no forecast line. The intel's "Leave out for 5.0.0" list includes time-phased forecasting.
- The portfolio curve sums the jobs with an approved estimate. A draft-estimate job, such as 26-010, is left out of the portfolio curve. Its job page shows no curve section.
- Every value on the curve comes from the functions in `curve.ts`. That module must not copy formulas; it calls into `cost-rollups.ts` (finding D11: do not add a fourth copy).
- Each chart point carries `data-*` attributes with its date and cents, so the verify run can read the values without parsing pixels.

### Data model sketch

There are no schema changes. The curve is a read.

```ts
// v5/src/server/curve.ts (sketch)
export type CurvePoint = {
	on: string; // YYYY-MM-DD, America/Los_Angeles
	plannedCents: number;
	earnedCents: number | null; // null after the cutoff
	actualCents: number | null; // null after the cutoff
};
export declare function jobCurve(companyId: string, jobId: string): Promise<{
	cutoffOn: string | null;
	points: CurvePoint[];
}>;
export declare function portfolioCurve(companyId: string): Promise<{
	cutoffOn: string | null;
	points: CurvePoint[];
}>;
```

### Out of scope for Part A

- Average Performance, dark theme, plan events, unknown-job copy, crews contract.
- A forecast line on the curve. Planned value from schedule activities (5.1.2).

## Part B: Average Performance forecast

Decision 2026-10-24: re-add Average Performance in 5.0.3. The plan promised two methods, and the method must be selectable per cost item. #675 removed it because no screen could select it.

**Migration: 0017** (builders own this number).

```sql
ALTER TYPE "public"."forecast_method" ADD VALUE 'average_performance';
```

**Files and areas.** `v5/src/db/schema.ts` enum, drizzle `0017_*.sql`, cost item page control, `costItem.setForecastMethod` in `assistant/actions.ts` and `route.ts`, EAC math in `v5/src/lib/ev.ts` / cost rollups.

### Rules

- The PM sets a leaf cost item's method on its cost item page from 5.0.2. The action goes through `run()` with `writes: true`, so the change appears in the job's change list. The executive, the superintendent, and the foreman are refused.
- Current Budget: item EAC = AC + (Current Budget − EV). This is the 5.0.0 formula.
- Average Performance: item EAC = locked AC ÷ locked percent complete (claim C15, inference I1).
  - Compute it as an exact fraction. For a units item, that is AC × budget quantity ÷ claimed quantity. Round to the cent once, at the item.
  - With 0% claimed, the item uses the Current Budget value and is labeled as a fallback, not as a division by zero.
- Job EAC is the sum of item EACs (claim C12). ETC = EAC − AC.
- The item shows its derivation next to the number, for example "EAC = $AC ÷ 40.0% (average performance)".
- A change order's new cost item starts on Current Budget (claim C23).

### Out of scope for Part B

- Other forecast methods (claim C16). Average Performance date windows (claim C15 leave-outs). Committed Cost (5.2).

## Part D: plan history timestamps (role + time)

Decision 2026-10-25: each plan's history shows the time of each submit, return, and approve, with the actor's **role**. Example: Cedar job's "Recount pour 3" shows Returned, then Approved, each with its time in the company's zone. Use append-only events. Do not show actor display names in the history list.

**Migration: 0018** (`0018_daily_plan_events.sql`).

**Files and areas.** `v5/src/db/schema.ts` (`dailyPlanEvents`), drizzle `0018_*`, writers in `v5/src/server/progress.ts` and plan submit/return/approve paths, `buildPlanHistory` in `v5/src/server/plan-page.ts`, seed in `v5/src/seed/`, plan page UI that renders role + local time.

### Why columns are not enough

`daily_plans` already has `submitted_at`, `returned_at`, `approved_at` (`0015_plan_history_columns`). Those hold the **last** stamp of each kind. A plan that is returned twice then approved keeps only one `returned_at`. `buildPlanHistory` today fills gaps from `action_runs` and shows **names** in `who`. Multi-return honesty and role display need an append-only table, the same shape as `change_order_events`.

### Data model

```ts
// v5/src/db/schema.ts (sketch)
export const planEventKindEnum = pgEnum("plan_event_kind", [
	"created",
	"submitted",
	"reported",
	"returned",
	"approved",
]);

export const dailyPlanEvents = pgTable(
	"daily_plan_events",
	{
		id: uuid("id").primaryKey().defaultRandom(),
		companyId: companyRef(),
		planId: uuid("plan_id")
			.notNull()
			.references(() => dailyPlans.id, { onDelete: "cascade" }),
		kind: planEventKindEnum("kind").notNull(),
		/** Role at the time of the command. Shown in the UI. */
		actorRole: roleEnum("actor_role").notNull(),
		actorId: uuid("actor_id").references(() => users.id, {
			onDelete: "set null",
		}),
		/** Return reason, or empty. */
		detail: text("detail").notNull().default(""),
		at: timestamp("at", { withTimezone: true }).notNull().defaultNow(),
	},
	(t) => [index("daily_plan_events_plan_idx").on(t.planId, t.at)],
);
```

Keep the existing stamp columns on `daily_plans` for queries that need "last submitted at". Writers update the stamp **and** insert an event in the same transaction.

### Backfill of existing seeded plans

Migration `0018` (or a seed-only path run from `db:seed` / demo reset) inserts events for every plan that already has history columns:

| Source column / state | Event `kind` | `actorRole` | `at` |
|---|---|---|---|
| `created_at` present | `created` | `superintendent` (seed author of plans) | `created_at` |
| `submitted_at` present | `submitted` | `superintendent` | `submitted_at` |
| `reported_at` or approved/reported status with report path | `reported` | `foreman` | report stamp or `submitted_at` + 1 hour when only status exists |
| `returned_at` + `return_reason` | `returned` | `superintendent` | `returned_at` |
| `approved_at` present | `approved` | `superintendent` | `approved_at` |

Do not invent names. Roles are enough. After backfill, `buildPlanHistory` reads **only** `daily_plan_events` ordered by `at`, and maps each row to UI copy that shows **role** and **time in the company zone** (America/Los_Angeles for the demo company). The `PlanHistoryEvent` type drops `who: string` in favor of `actorRole: Role` (and optional `detail`).

## Part E: rail unknown-job refusal

Decision 2026-10-25: keep refusing to create a plan on a job that does not exist. Job creation is out of scope for 5.x field work. The refusal names the job number it could not find and offers up to 3 of the user's real jobs as choices.

**Files and areas.** `unknownJob()` in `v5/src/server/assistant/actions.ts` only (and unit coverage next to other assistant action tests). No migration.

### Rules

- Cap choices at **3**.
- List only jobs the signed-in user's company portfolio already returns, with `estimateStatus === "approved"` (or the same draft filter `getPortfolio` / plan create use). **Exclude draft jobs** such as Harbor **26-010**.
- Prefer stable order: job number ascending.
- If the user has more than 3 approved jobs, take the first 3 in that order.
- If the user has 1 approved job, offer that one. If none, name the missing number and offer no choices.

### Exact refusal wording

Implement these templates with no extra sentences:

- One or more choices (N is 1 to 3):  
  `There is no job {number}. Try {job1}`  
  or `There is no job {number}. Try {job1} or {job2}`  
  or `There is no job {number}. Try {job1}, {job2}, or {job3}`.
- Zero choices:  
  `There is no job {number}.`

Set `refused: true`. The rail chip stays on the existing "Couldn't …" path for create when the router maps through this helper.

Today's body (replace it):

```ts
summary: `There is no job ${number} in this sandbox. Jobs here: ${all.map((j) => j.job.number).join(", ")}.`,
```
