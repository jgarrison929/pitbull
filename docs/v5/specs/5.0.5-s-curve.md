## Why this increment

[Fresh-start plan section 4](../fresh-start-plan.md#4-500-core-the-smallest-credible-ineight-style-story), step 5, asks for "an S-curve chart". No chart is on `main` yet.

5.1 Schedule moves planned value from each cost item's own dates onto the schedule (plan section 9). The S-curve is where that move shows, so it ships before 5.1.2.

InEight's time-phased budget spreads each cost item's current budget between its start and finish dates, and SPI needs that spread (claims C8 and C9 in [cost and earned value intel](../intel/cost-and-earned-value.md)). The intel concludes that daily linear planned value "is enough for the S-curve the plan asks for" (I4).

## User stories

1. As the executive on the portfolio, I see one curve of planned, earned, and actual cost across the active jobs, and I can tell at a glance whether the company is ahead or behind.
2. As the PM on a job, I see the same curve for that job. Its values at the cutoff match the KPI tiles to the cent.

## Scope

**Files and areas.** New `v5/src/server/curve.ts` with `jobCurve` and `portfolioCurve`. Job page and portfolio page chart sections. Theme-token SVG chart (three polylines — no Recharts client bundle). Shared CB / EV / PV SQL lives in `v5/src/server/cost-rollup-exprs.ts`; both `cost-rollups.ts` and `curve.ts` import it (intel D11). No schema change.

### Rules

- One point per calendar day in America/Los_Angeles, from the job's earliest cost-item planned start to its latest planned finish. The cost and earned value intel logs the UTC date problem as finding D7.
- Planned value is cumulative and linear between each leaf cost item's planned start and finish, on Current Budget. It is the same function the PV tile uses. The last planned-value point equals the job's Current Budget total.
- Earned value and actual cost follow the one-cutoff rule from #666. Both lines stop at the cutoff, which is the date of the last locked claim.
  - Earned value changes only on lock dates.
  - Actual cost is cumulative by cost-entry date. From 5.0.2 on, field labor is dated with the plan date.
  - Cost posted after the cutoff shows in the "since lock" tile, as it does today, and not on the curve.
- The curve has no forecast line. The intel's "Leave out for 5.0.0" list includes time-phased forecasting.
- The portfolio curve sums the jobs with an approved estimate. A draft-estimate job, such as 26-010, is left out of the portfolio curve. Its job page shows no curve section.
- Every value on the curve comes from the functions in `curve.ts`. That module must not copy formulas; it imports the same `cost-rollup-exprs.ts` fragments that `cost-rollups.ts` uses (finding D11: one definition only).
- Each chart point carries `data-*` attributes with its date and cents, so the verify run can read the values without parsing pixels.
- The chart uses the theme tokens in `globals.css`, light and dark, as 5.0.3 Part C requires of every chart.

### Data model sketch

There are no schema changes. The curve is a read.

```ts
// v5/src/server/curve.ts (sketch)
export type CurvePoint = {
	on: string; // YYYY-MM-DD, America/Los_Angeles
	plannedCents: number;
	earnedCents: number | null; // null after the cutoff
	actualCents: number | null; // null after the cutoff
};
export declare function jobCurve(companyId: string, jobId: string): Promise<{
	cutoffOn: string | null;
	points: CurvePoint[];
}>;
export declare function portfolioCurve(companyId: string): Promise<{
	cutoffOn: string | null;
	points: CurvePoint[];
}>;
```

## Acceptance checks (staging)

These are checks 1 to 6 from the 5.0.3 spec, unchanged. Run every check on staging (`https://pitbull-web-staging.up.railway.app`) on a fresh sandbox. Curve values come from `data-*` on chart points. Tile values come from the KPI strip.

1. **The PV line ends at the budget.** Role: PM. Open `/app/jobs/25-031`. Expected: the last planned-value point equals the Current Budget tile, to the cent.
2. **The cutoff matches the tiles.** On the same page, at the cutoff date, the earned, actual, and planned values on the curve equal the EV, AC, and PV tiles, to the cent. Repeat on 24-118 and 24-077.
3. **A lock moves the cutoff.** As the PM, lock Period 2 on 25-031. Expected: the cutoff moves to today (PT), and the curve's earned and actual values at the new cutoff equal the new tiles.
4. **A change order moves the PV line.** As the PM, approve the priced CO-001 ($60,000.00) on 25-031. Expected: the last planned-value point rises by exactly $60,000.00.
5. **Portfolio curve.** As the executive on `/app`, the last planned-value point equals the sum of the Current Budget totals of 24-118, 25-031, and 24-077. The values at the cutoff equal the portfolio tiles.
6. **Draft jobs have no curve.** On `/app/jobs/26-010`, there is no curve section, and the page shows no empty chart.

The 5.0.3 crawl check (5.0.3 check 11) still runs in both themes and must pass on the pages with a chart, each under 1.5 s.

## Out of scope

- A forecast line or a time-phased forecast on the curve.
- Cost curves other than linear (claim C9 lists curve shapes).
- Planned value from schedule activities (5.1.2).
- Average Performance, the dark theme, plan events, unknown-job copy, and the crews contract. Those shipped in 5.0.3.

## Trust-bar risks

- **Page speed (item 1).** The chart is a server SVG (no chart-library JS). Job and portfolio pages must stay under 1.5 s on staging.
- **One formula (item 6).** If the curve computes planned value its own way, check 2 fails on any job with a change order. One definition in `cost-rollup-exprs.ts`; rollups and curve both import it.
- **Cutoff honesty (item 3).** The curve shows one cutoff, the same as the tiles.
- **Empty states (item 1).** A job with no locked claim has no cutoff. Its curve shows planned value only, with the note "Earned and actual cost appear after the first locked period".
